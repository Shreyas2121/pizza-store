# Deploy free: Render + Vercel + Neon + Cloudinary

`render.yaml` creates one **free** Render backend. `frontend/vercel.json` configures the Vite frontend for Vercel Hobby. No paid disks or cron services are provisioned. New files use the existing Cloudinary account with a separate `pizzastore/` namespace, so stay-mate assets are unaffected.

## Existing images and new uploads

Existing public images are bundled in `backend/assets/uploads`. Startup copies them to local `uploads/` without overwriting files. Their database URLs stay exactly as they are: `/uploads/...` and `/api/v1/uploads/...` both work. No image URL migration or Cloudinary re-upload is required for those bundled files.

New product/menu images go to Cloudinary under `pizzastore/catalog/`, with HTTPS URLs stored in the existing image columns. New promotion images go under `pizzastore/promotions/` while preserving the schema's relative `/uploads/promotions/...` URL contract; requests for those new files redirect to Cloudinary. Bundled legacy promotion images are served directly. Every frontend image renderer accepts both backend-relative paths and Cloudinary URLs.

New expense receipts use **authenticated raw** Cloudinary assets under `pizzastore/expense-receipts/`. Downloads still pass through the existing permission checks; the backend retrieves bytes with a short-lived signed API URL and does not send that URL to the browser. Receipt keys retain the existing database format, so this storage change needs no schema migration.

Previously created local private receipts are not bundled or committed. They must be transferred separately before their existing records can be downloaded on the deployed host. New local uploads made after these assets were bundled also need Cloudinary upload or an explicit public bundle update.

## Render setup

Push the changes and create a Render Blueprint from `render.yaml`. Or create a Node web service manually using these settings:

| Setting | Value |
| --- | --- |
| Plan | Free |
| Root directory | Repository root (leave blank) |
| Build command | `npx --yes pnpm@12.9.1 install --frozen-lockfile --prod=false && npx --yes pnpm@12.9.1 --filter backend build` |
| Start command | `cd backend && node dist/index.js` |
| Health check | `/health/ready` |
| Node version | `22.23.2` |

The Blueprint sets the following options automatically; enter them yourself for a manual setup:

```env
NODE_ENV=production
IMAGE_STORAGE=cloudinary
MAINTENANCE_ENABLED=true
PAYMENT_PROVIDER_MODE=simulator
RAZORPAY_ENABLED=false
```

Supply these **backend-only** values:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Existing Neon application URL, including `sslmode=require` |
| `FE_URL` | Exact Vercel HTTPS origin, without a trailing slash |
| `CLOUDINARY_CLOUD_NAME` | Same account value used for stay-mate |
| `CLOUDINARY_API_KEY` | Same account value used for stay-mate |
| `CLOUDINARY_API_SECRET` | Same account value used for stay-mate |
| `PAYROLL_ENCRYPTION_KEY` | Stable secret of at least 32 characters; preserve the existing key for already encrypted payroll data |
| `JWT_SECRET` | At least 32 random characters; generated by the Blueprint |
| `METRICS_BEARER_TOKEN` | Separate token of at least 32 characters; generated by the Blueprint |

Keep secrets stable across redeploys. Do not copy server secrets into Vercel `VITE_` variables. The code uses the same Cloudinary credential names as stay-mate, but credentials are not embedded in these files or copied between projects.

The backend accepts Render's default `PORT=10000`, prepares bundled assets, and verifies Neon before accepting traffic. Failed startup exits non-zero. `/health/ready` returns 503 when database queries fail; `/health/live` checks process liveness.

## Vercel setup

Import the repository using:

| Setting | Value |
| --- | --- |
| Root directory | `frontend` |
| Framework | Vite |
| Build command | `pnpm build` |
| Output directory | `dist` |
| `VITE_BACKEND_URL` | Render HTTPS origin, without `/api/v1` |

Use the workspace lockfile and pinned package manager. Allow access to files outside the root directory if Vercel requests it for workspace installation. Set `VITE_BACKEND_URL` before building; changing it requires redeployment. Builds reject missing or malformed backend origins. The SPA rewrite supports refreshing nested routes while preserving static asset delivery.

Update Render's `FE_URL` to the final production frontend origin. HTTP and Socket.IO share that origin. Arbitrary Vercel preview origins are not allowed automatically.

## Existing Neon schema

Do not reset or reseed the database for deployment. These hosting/storage changes do not introduce a database migration.

Check that the existing database matches the committed schema. A database provisioned with `db:push` may not have a matching migration journal; blindly applying the baseline can fail. Review pending migrations on an isolated Neon test branch first. Only after verifying the journal, run existing pending migrations with a **direct** Neon URL (without `-pooler`) supplied as `DATABASE_MIGRATION_URL`:

```sh
pnpm --filter backend db:migrate
```

Migration configuration requires only a database URL, not application secrets. Migrations remain separate from server startup. No migration, seed or database reset was run while preparing these files.

## Recovery and free-tier behavior

`MAINTENANCE_ENABLED=true` starts bounded maintenance tasks immediately and then periodically:

- Financial event posting every minute.
- Expired reservation recovery every five minutes.
- Provider payment recovery every five minutes when using `razorpay_test`.

Each task prevents overlapping runs, reports its results, retries after failures and drains active work on shutdown. Timers stop when Render sleeps and resume at startup. They do not send keep-alive traffic. This is suitable for a portfolio demo; it does not provide an always-running schedule. Inspect failed items and reservation conflicts in logs.

For optional Razorpay **test mode**, supply all three provider secrets, set `PAYMENT_PROVIDER_MODE=razorpay_test` and `RAZORPAY_ENABLED=true`, and point the provider webhook at `https://BACKEND/api/v1/payments/razorpay/webhook`. Live payments remain unsupported. Simulator state is process-local and resets on restart.

Render Free sleeps after idle periods, so the first request can take time. Its 750 free instance hours are shared across a Render workspace; stay-mate and this backend consume the same allowance if hosted in the same workspace. There is no persistent local disk, so only bundled public files and Cloudinary files survive restarts. Vercel Hobby cannot provide the frequent cron schedule this demo needs, so this setup uses the backend timers instead.

## Verify before sharing

1. Check `/health/ready` and `/uploads/pizza-1.avif` on the deployed backend.
2. Open and refresh `/docs/reliability` on Vercel.
3. Check existing product images, login, cart, simulator checkout and Socket.IO updates.
4. Upload a new product/promotion image, restart the backend, and verify its Cloudinary image still loads.
5. Upload a receipt, verify authorized download and unauthorized rejection, and confirm it survives restart. Check authenticated raw downloads with the Cloudinary account; PDF delivery may require account security settings.
6. Check maintenance results for posting failures, expired reservations and conflicts.

Local checks do not establish hosted browser behavior, Cloudinary account settings, provider callbacks or database migration state.
